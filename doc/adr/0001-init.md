# ADR 0001: Initial Architecture & Phase 1 Sandbox Engine

- **Status**: Accepted
- **Deciders**: WinPhay
- **Date**: 2026-11-11

## Context & Problem Statement
Autonomous coding agents require local command execution to build, test, and debug code. However, giving an LLM direct terminal access to a developer's workstation risks catastrophic data loss (`rm -rf`), credential leakage, and context window pollution from verbose logs. Cloud sandboxes introduce high subscription costs and round-trip network latency.

## Decision Outcome
Chosen option: Develop **Vessel** as a local Go daemon exposing an MCP server interface that executes agent commands inside an isolated Docker container with Copy-on-Write snapshot checkpoints and token-optimized stdout scrubbing.

### Positive Consequences
- **Host Protection**: Host filesystem outside `/workspace` is completely shielded from agent mistakes or rogue commands.
- **Fast Local Feedback**: <5ms IPC latency over stdio MCP protocol; zero recurring cloud fees.
- **Time-Travel Rollback**: Agents can test risky modifications and restore clean states via `vessel_rollback` in <1s.
- **Token Efficiency**: In-daemon ANSI scrubber prevents terminal progress bars and color codes from blowing LLM token limits.

### Negative Consequences / Trade-offs
- Phase 1 relies on Docker daemon availability on the host machine.
- RAM state snapshotting is deferred to Phase 2 (MicroVM / KVM engine); Phase 1 provides filesystem-level checkpoints via container tags.

## Invariants Established
1. No untrusted agent commands run directly on the host machine.
2. Only the target project directory is mounted into the container at `/workspace`.
3. Changes to the MCP tool surface require a new ADR.
